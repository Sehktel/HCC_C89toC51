Вот как “человек-компилятор” проходит `lexNumber`:

- Смотрю сигнатуру: `lexNumber :: String -> (Token, String)`  
  Значит, функция берет входную строку и возвращает пару: распознанный токен + непрочитанный хвост.

- Иду по уравнениям сверху вниз:
  1. `('0':'x':rest)` и `('0':'X':rest)` — если число начинается с `0x`/`0X`, это hex, передаем в `lexHexNumber`.
  2. `('0':rest@(d:_)) | isDigit d` — если после `0` идет цифра, это кандидат на octal-форму `0...`.
  3. `('0':rest)` — если просто ноль и дальше не цифра, это литерал `0`.
  4. `input = ...` — fallback: обычное десятичное число, читаем `span isDigit`.

---

Как именно читать ветку octal (ключевая часть):

```haskell
let (numberDigits, tailRest) = span isDigit rest
    literal = '0' : numberDigits
 in if hasInvalidOctalDigit numberDigits
      then (TokenLexError ("Invalid octal literal: " ++ literal), tailRest)
      else attachIntegerSuffix (readOctal literal) tailRest
```

Логика в голове такая:

1. После первого `0` забираю подряд все цифры (`span isDigit`).
2. Склеиваю полный текст литерала `literal` (например `075`).
3. Проверяю, нет ли “запрещенных для octal” цифр (8, 9).
4. Если есть — отдаю `TokenLexError`.
5. Если нет — читаю как octal (`readOctal`) и затем обрабатываю суффикс (`attachIntegerSuffix`).

---

Как это связано с синтаксисом языка:

- Лексер здесь кодирует правило языка:  
  `0x...` → hex, `0...` → octal, иначе → decimal.
- Порядок матчей задает **приоритет синтаксических форм**: сначала префиксные спец-формы, потом более общие.
- Это типичный стиль для лексера: “самое специфичное раньше, самое общее в конце”.

**Cursor**

Определяется в стандартной библиотеке Haskell, в модуле `Data.Maybe` (и автоматически доступно через `Prelude`).

Каноническое определение такое:

```haskell
data Maybe a = Nothing | Just a
```

Где:

- `Maybe` — параметризованный тип-контейнер (“значение может быть или отсутствовать”),
- `Nothing` — конструктор “значения нет”,
- `Just` — конструктор “значение есть” (`Just x`).

Практически в твоем проекте ничего дополнительно импортировать не нужно, потому что `Prelude` уже реэкспортирует `Maybe(..)`.

Если хочешь посмотреть “глазами GHC” в REPL:

- `:t Just` → `Just :: a -> Maybe a`
- `:t Nothing` → `Nothing :: Maybe a`
- `:i Maybe` → покажет объявление типа и конструкторов.

data IntSuffix

- Вы явно кодируете конечный набор суффиксов целых литералов C89: `U`, `L`, `UL`.

- В `ghci`:

- `:i Maybe`
- `:i Just`
- `:i Eq`
- `:i Show`
- `:i deriving` → не сработает как с именем, потому что это keyword синтаксиса, не идентификатор.

Как отличать быстро “на глаз”:

- **keyword языка** (`data`, `case`, `deriving`, `where`) — не имеют `:i` как обычные имена.
- **Typeclass** (`Eq`, `Show`, `Ord`) — `:i` покажет `class ...`.
- **Тип/конструктор** (`Maybe`, `Just`, `Nothing`) — `:i` покажет `data ... = ...`.
- **Функция** (`span`, `map`) — `:i`/`:t` покажет сигнатуру `a -> b`.

- наведи курсор (hover) на слово;

**Cursor**

Отлично, это как раз DSL `hspec` — читается почти как “текст спецификации”.

Твоя строка (с поправкой):  
`describe "123" $ do it "456" $ do lexer "a" \`shouldBe\` [TokenIdentifier "a"]`

Разбор по частям:

- `describe "123" $ do ...`  
  Группа тестов с именем `"123"`.  
  `describe` принимает заголовок и блок вложенных тестов.

- `it "456" $ do ...`  
  Один конкретный тест-кейс с именем `"456"`.

- `$`  
  Оператор “применить справа налево, без лишних скобок”.  
  То есть:
  - `describe "123" $ do ...` == `describe "123" (do ...)`
  - `it "456" $ do ...` == `it "456" (do ...)`

- `do ...`  
  Блок из нескольких действий в `IO`/`SpecM`-контексте.  
  Внутри можно писать несколько проверок подряд.

- ``shouldBe``  
  Ассерция равенства: “фактическое значение должно быть равно ожидаемому”.  
  Если не равно — тест падает.

- `lexer "a"`  
  Вызов тестируемой функции.

- `[TokenIdentifier "a"]`  
  Ожидаемый результат (список токенов).

Важная поправка в твоем примере: должно быть **`it`**, не `if`.  
`if` — это keyword языка Haskell для условий, к Hspec-тестам не относится.

Мини-аналог на “обычном языке”:

- `describe` = “раздел/контекст”
- `it` = “конкретное утверждение”
- `shouldBe` = “должно быть равно”

- `mapM  :: (a -> m b) -> [a] -> m [b]` — выполняет эффекты и **возвращает список результатов**
- `mapM_ :: (a -> m b) -> [a] -> m ()` — выполняет эффекты, результаты **выбрасывает**

`forM_` — это тот же `mapM_`, только аргументы переставлены для более читаемого стиля:

- `mapM_ f xs`
- `forM_ xs f`

В тестах тебе нужен именно эффект “добавить тест-кейс”, а не список результатов — поэтому `_`-версия логична.

Почему разный регистр:
- в Haskell имена обычных функций начинаются с маленькой буквы (`forM_`),
- заглавные буквы обычно у типов/конструкторов (`Maybe`, `Just`, `TokenInt`).
- `M` внутри имени — просто часть имени по историческому соглашению (`mapM`, `forM`, `foldM`), не отдельный синтаксис.

### Как это читать

1. **Сигнатура** `String -> String`: на вход целый исходник одной строкой, на выход — тоже одна строка.

2. **Композиция `.`** в Haskell **читается справа налево**: сначала то, что ниже в списке, потом выше.

   Для любого `s :: String` эквивалентно:

   ```haskell
   preprocess s =
     unlines
       ( filter (not . null)
           ( map trim
               ( lines ( replaceTrigraphs s )
               )
           )
       )
   ```

   То есть порядок этапов такой:

   | Шаг | Функция | Смысл |
   |-----|---------|--------|
   | 1 | `replaceTrigraphs` | Подмена C89-триграфов (`??=` → `#` и т.д.) в сыром тексте. |
   | 2 | `lines` | Разбить текст на список строк (по переводам строк). |
   | 3 | `map trim` | У каждой строки убрать пробелы с начала и конца (`trim`). |
   | 4 | `filter (not . null)` | Выкинуть строки, которые после `trim` стали пустыми. |
   | 5 | `unlines` | Склеить строки обратно в один `String`, между ними снова ставятся переводы строк. |

3. **`filter (not . null)`** — оставить только непустые строки: `null` проверяет, пуст ли список символов; `not . null` — предикат «строка не пустая».

4. **Почему нет явного аргумента** у `preprocess`: запись `preprocess = f . g` означает «`preprocess` — это функция, равная композиции»; аргумент подставится при вызове `preprocess input`.

## Почему вообще “так должно быть”

Исторически и по стандартам “текстовая строка” — это содержимое **до** `\n`, а `\n` — **разделитель строк**.

### 1) POSIX (текстовые файлы)
В POSIX понятие “line” привязано к завершающему newline.  
Если последняя “строка” без `\n`, это уже не совсем каноничная “line” в POSIX-смысле.

### 2) C-стандарт (для исходников особенно важно)
Для C исходник традиционно должен заканчиваться newline (и не заканчиваться обратным слешем перед ним).  
Идея: чтобы фазы трансляции работали однозначно и не было краевых неоднозначностей на конце файла.

## Почему это практически важно

- корректные `diff`/`patch`/`cat`/старые тулзы;
- отсутствие “No newline at end of file” в git diff;
- предсказуемая склейка/парсинг строк;
- меньше краевых багов в генераторах кода и препроцессорах.
