Ниже — примеры того, что **разумно считать «неизвестным» (неподдержанным) до доработки парсера/AST**, опираясь на текущую логику `Parser` (`AstUnknown`, обрыв разбора, «одна декларация в файле», отсутствие `switch`/`do` и т.д.).

### 1. Явно сворачивается в `AstUnknown` по правилам входа

- **Файл из одной глобальной декларации** — сейчас это специальный случай: не `AstProgram`, а `AstUnknown` (см. тест с `int x;`).

### 2. Конструкции, которые разбор **не доводит** до нормального дерева (часто весь файл → `AstUnknown`)

- **`switch` / `case` / `default`** — в `parseStatement` нет веток; тело вида `switch (e) { ... }` упирается в разбор выражения до `;` и ломается.
- **`do ... while (...);`** — аналогично, нет ветки `TokenDo`.
- **Составные объявления со вложенными `{ ... }` и «первой точкой с запятой»** — в `parseDeclaration` обрезка идёт по **первому** `TokenSemicolon`, без учёта скобок, поэтому типичные **`struct` / `union` с полями**, **`enum` с перечислителями** и т.п. дают **неверный срез токенов** и дальше обычно «ломают» единицу трансляции → хвост токенов / ошибка → **`AstUnknown`**.
- **Сложные деклараторы** (указатели, массивы в деклараторе, функции как параметры и т.д.), например **`int (*fp)(void);`**, **`void foo(int *p);`** — для **определения функции** в комментарии к парсеру указано ограничение: только **простой идентификатор** после спецификаторов; для деклараций — сырой список токенов до `;`, что на граничных формах легко расходится с реальной грамматикой.

### 3. Пока **нет отдельного узла AST** (формально может «пройти» как мусор)

- **`break;` / `continue;` / `goto L;`** — часто уйдут в **`AstExpr` как сырой набор токенов** (через expression-statement), без семантики «оператор перехода». Их **логично считать неизвестными в смысле IR**, пока не появятся отдельные узлы или хотя бы явный «неподдержано».

### 4. Вне фронтенда (лексер / препроцессор)

- **`#include`, `#define`, условная компиляция** и т.д. — пока препроцессор и лексер не соответствуют полному C, много реальных файлов будет либо **не тем потоком токенов**, либо с ошибками лексера; это отдельный пласт «неизвестного», не только AST.

Что стало лучше:

- Для **типичных** `switch` / `case` / `default` / `do … while` дерево **структурировано** (`AstSwitch`, `AstCase`, `AstDefault`, `AstDoWhile`), а не сваливается в `AstUnknown` целикого файла — это реальное усиление **синтаксического** каркаса и регрессионных тестов на фикстурах.

## Операции `*`, `+`, `++`, `--`, `?` …

В **C89 нет оператора `**`** (в Python-стиле); подряд идут два `TokenMultiply`.  
Лексер уже отдаёт отдельные токены: `TokenPlus`, `TokenMultiply`, `TokenPlusPlus`, `TokenMinusMinus`, `TokenQuestion`, `TokenColon` и т.д.

**Семантики приоритетов в AST нет:** во `AstExpr` / `AstReturnExpr` лежит **линейный** список токенов в порядке слева направо, например `a + b * c` → `[Identifier "a", Plus, Identifier "b", Multiply, Identifier "c"]`.  
Порядок **не врёт** относительно исходного текста, но **дерева «кто к чему привязан» нет** — его придётся восстанавливать при спуске в IR (или ввести отдельный слой `Expr`). Для тернарного оператора то же: будет последовательность с `?` и `:`, без вложенности в узлах.

## «Одна глобальная декларация → `AstUnknown`» — плохо ли?

**Не катастрофа, но спорно и часто мешает.**

### 1. Выражения «плоские»

**Идея:** в нормальном AST выражение — **дерево**: у узла «+» два ребёнка (левое и правое подвыражение), приоритет и скобки закодированы в форме дерева.

**У вас сейчас:** для большинства выражений парсер кладёт в узел **`AstExpr [Token, Token, …]`** — просто **список токенов подряд**, без вложенности.

**Пример исходника:**

```c
return a + b * c;
```

**Мысленно по стандарту C:** `*` жёстче `+`, дерево такое: `+(a, *(b,c))`.

**Что у вас по сути:** что-то вроде плоского списка токенов  
`a`, `+`, `b`, `*`, `c` — порядок сохранён, **но «кто к кому относится» в типе AST не записано**. Любой следующий этап (оптимизации, проверка типов) должен **снова** разбирать приоритеты из этого списка или вы должны позже ввести настоящее `Expr`.

**Про `*`, `+`, `++`, `--`, `?`:** лексер выдаёт правильные токены (`*`, `+`, `++`, `--`, `?`, `:` и т.д.), но **семантика** «это инкремент, а не два плюса» / «это тернарный оператор» в дереве **не выражена отдельными узлами** — всё лежит в одной «ленте» токенов.

---

### 2. Деклараторы «плоские»

**Декларатор** — это часть объявления после типа: указатели, имя, скобки `[]`, `(params)` и т.д.

**Примеры:**

```c
int *p;
int arr[10];
void foo(int x);
int (*fp)(void);
```

Сейчас объявление на верхнем уровне часто уходит в **`AstDeclaration [Token …]`** — снова **сырой список токенов до `;`**, без отдельных узлов «указатель», «массив размера 10», «указатель на функцию».

Последствие: вы **не спрашиваете** у дерева «какой тип у `fp`» — только перечитываете токены.

---

### 3. «Одна глобальная декларация → `AstUnknown`»

В `parseTokens` есть специальная ветка: если после разбора всего файла получился **ровно один** узел и это **`AstDeclaration`**, результат **заменяется** на `AstUnknown` со всеми исходными токенами.

**Пример:**

```c
int x;
```

Для человека и для C это **нормальная** единица трансляции (только объявление).

Для вашего парсера сейчас это **намеренно** превращается в `AstUnknown`, чтобы не выдавать «программу из одной декларации» как полноценный `AstProgram`. Это **не ошибка исходника**, а **ограничение/хак** текущей реализации.

**Пример, где это не срабатывает:**

```c
int x;
int main(void) { return 0; }
```

Тут узлов два → обычный `AstProgram` с двумя элементами.

---

### 4. `struct { … };` и «сложные» декларации

**Пример:**

```c
struct S {
  int x;
};
int main(void) { return 0; }
```

Внутри `struct` есть **`;` после `int x;`**. Ваш `parseDeclaration` для верхнего уровня режет объявление по **первому** `;`. В итоге «объявление `struct S { int x`» обрывается не там, дальше поток токенов **не сходится** с ожидаемой грамматикой → часто **`AstUnknown` на весь файл** или иной сбой.

То же класс проблем: **enum с телом**, **typedef** со сложной формой и т.д., пока нет нормального разбора скобочных областей в декларациях.

## Тонкости стандарта C (вокруг «приоритетов»)

**1. Нормативно задаётся грамматикой, а не «таблицей из учебника».**  
В стандарте разбор следует из правил для *expression*; удобная таблица приоритетов в приложении/справочнике — это **сводка** с той же семантикой группировки. Для компилятора важна именно **согласованность с грамматикой** C89/C99/…

**2. Приоритет ≠ порядок вычисления.**  
Дерево разбора говорит только о том, **какие подвыражения с чем склеены**. Порядок вычисления аргументов многих операторов **не задаётся** жёстко; с этим связаны отдельные правила про *sequence points* и неопределённое поведение. Тесты на **форму дерева** это не проверяют — и правильно.

**3. Ассоциативность.**  
Большинство бинарных операторов **левоассоциативны** (`a-b-c` → `(a-b)-c`). **Правая** ассоциативность у присваивания и у условного `?:` (`a?b:c?d:e` → `a ? b : (c ? d : e)`). Унарные цепочки тоже имеют свои правила (справа налево для префиксных в классическом описании).

**4. Цепочки сравнений — частая ловушка.**  
Выражение `a < b < c` в C **не** означает «между a и c лежит b». Это `(a < b) < c` (результат первого сравнения — 0 или 1 — сравнивается с `c`). Семантически это почти никогда не то, что хотят с математической записи.

**5. Смешение побитовых и логических операций.**  
Операторы `&`, `^`, `|` образуют свой уровень; **`&&` и `||`** — ниже, с **коротким замыканием** (вторая часть может не вычисляться). Поэтому «похожие» символы ведут себя по-разному и по разбору, и по выполнению.

**6. Смешение побитовых и равенства.**  
Для выражений вроде `a & b == c` важно помнить: **`==` и `!=` группируются на другом уровне, чем `&`** (в стандартной иерархии равенство и отношения отделены от побитового И). Итоговое дерево может не совпадать с интуицией «сначала все побитовые». Именно такие места полезно **дублировать скобками** в исходнике и в тестах.

**7. Сдвиги и арифметика.**  
Операторы сдвига `<<` / `>>` стоят **отдельным уровнем** от `+` и `*`. Поэтому комбинации вроде `a << b + c` и `a + b << c` дают разные деревья; путаница здесь именно стандартная, а не «ошибка компилятора».

**8. Тернарный оператор и вложенность.**  
Вложенные `?:` без скобок разбираются по правилам **правой ассоциативности**; середина — это выражение до **«своего»** `:` при учёте вложенных `?` (у вас в парсере это отражено через `splitAtTernaryColon`).

**9. Подмножество реализации.**  
У вас в парсере нет полных **приведений типов** `(T)expr`, `sizeof(тип)` и т.д.; для них в полном C свои уровни и неоднозначности (граница между кастом и вызовом с `(`). Пока это не реализовано, «полное соответствие стандарту по всем выражениям» формально не формулируется.

**10. C и C++.**  
В мелочах (например, некоторые комбинации с `const`, перегрузки в C++) деревья могут различаться; для проекта **C89 + C51** ориентир — именно **C**.

## C89 и C90 — в чём разница

**По языку — никакой.** Это одна и та же первая стандартизированная версия C, просто два имени:

| Имя | Откуда | Год / документ |
|-----|--------|----------------|
| **C89** | ANSI | **1989** — ANSI X3.159-1989 |
| **C90** | ISO | **1990** — ISO/IEC 9899:1990 |

ISO приняла тот же стандарт чуть позже, поэтому год в названии другой. В текстах пишут и **ANSI C**, и **ISO C**, и **C89/C90** — обычно имеют в виду одно и то же (не путать с **C99**, **C11** и т.д.).

Иногда «C90» используют, чтобы подчеркнуть именно **международный** документ ISO; «C89» — **американский** ANSI и год первой публикации. Для вашего проекта логично везде говорить **C89** и при желании один раз оговорить синоним **ISO C90**.

В `Parser.hs` формулировку поправил: зафиксирован ориентир **C89**, в скобках — официальные обозначения и пояснение, что «C90» — то же по сути.
