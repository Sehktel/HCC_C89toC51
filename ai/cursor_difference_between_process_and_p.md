В вашем манифесте это **не два этапа одного и того же пайплайна**, а **два разных типа кейсов** для раннера `ManifestRunner_test`.

## `Parser`

- Поле `"package": "Parser"` означает: внутри теста вызывается **ваш компиляторный парсер** — `parseTokens (lexer source)` (см. `ManifestRunner_test.hs`).
- Результат сравнивается с **золотым файлом** (`outputFile`, например `test1.p`) по **текстовой** ожидалке (`shouldBe`, `shouldContain` и т.д.).
- `"process": null` — внешняя команда не запускается.

То есть это **golden-тест стадии «лексер → парсер»** в том же процессе, что и `hspec`.

## `Process`

- Поле `"package": "Process"` означает: **не** вызывается `Parser` из `src`; вместо этого выполняется **внешняя программа** через `System.Process.rawSystem` с полями `process.command` и `process.args`.
- Проверяется **код выхода** (`expectation` с `kind: "exitCodeShouldBe"`), а не текст AST/токенов.
- В примере из манифеста это даже `whoami` — чисто **иллюстрация контракта** «подпроцесс + exit code», а не парсинг C.

Итого: **`Parser` — про результат парсинга в Haskell; `Process` — про запуск произвольной команды и её exit code.** Имена `inputFile` / `outputFile` для кейса `Process` в текущем `runProcessCase` на проверку не влияют (файлы всё равно читаются в общем `assertManifestCase` до ветвления — это скорее общий шаблон записи кейса, чем логика теста).

**Замечание по дизайну:** строка `"package": "Process"` легко путается с «препроцессором» или «process stage» компилятора; по смыслу это ближе к чему-то вроде `Subprocess` или `ExternalCommand`. Если позже захотите тестировать именно CLI компилятора — логичнее явно назвать пакет и ожидания (stdout/stderr + код), чтобы не смешивать с парсером в памяти.

Они совпадают не потому, что **Process как-то «использует» результат парсера**, а потому что в манифесте у всех кейсов **одна и та же форма записи**: у каждого есть `inputFile` и `outputFile`, и третий кейс, скорее всего, **скопирован с парсерного** как шаблон.

По факту в коде:

```28:43:d:\Work\2026\HCC_C89toC51\tests\ManifestRunner_test.hs
assertManifestCase mc =
  it ("manifest: " ++ mcName mc ++ " [" ++ mcPackage mc ++ "]") $ do
    source <- readFile (mcInputFile mc)
    expected <- readFile (mcOutputFile mc)
    case mcPackage mc of
      "Lexer" -> do
        let actual = show (lexer source)
        assertTextExpectation mc actual expected
      "Parser" -> do
        let actual = show (parseTokens (lexer source))
        assertTextExpectation mc actual expected
      "Process" ->
        runProcessCase mc
```

Для **`Parser`** имеет смысл пара `test1.c` → `test1.p`: вход — исходник, эталон — вывод парсера.

Для **`Process`** ветка `runProcessCase` **ни `source`, ни `expected` не использует** — только `process { command, args }` и ожидание по коду выхода. Файлы всё равно читаются до `case`, то есть пути **формально те же**, но для этого примера они **лишние**: подошли бы любые существующие файлы или вообще потребовалась бы другая схема JSON, если бы раннер не читал их заранее.

**Итог:** одинаковые пути — это **наследие единого формата кейса + копипаст**, а не смысловое «Process = парсер в тот же файл». Если хотите убрать путаницу, имеет смысл либо не читать `input`/`output` для `Process`, либо вынести для него отдельные поля (например только `command`/`args`) и не требовать `.p` для таких кейсов.

Проверяю документацию проекта на заявленное назначение `Process`.



`Process` в манифесте нужен не как этап компилятора, а как **второй класс проверок в той же схеме «манифест → раннер»**.

**Зачем это по смыслу**

1. **Lexer / Parser** в манифесте проверяют **чистый Haskell**: строка на входе → `show` результата → сравнение с эталонным файлом. Внешний мир не участвует.

2. **`Process`** проверяет **внешнюю команду**: запуск `command` + `args`, ожидание вроде `exitCodeShouldBe`. Это нужно для сценариев, которые **нельзя** честно свести к «вызвали функцию и сравнили строку»:
   - CLI вашего `hcc-c89toc51` (или обёртки);
   - вызов Keil/C51, `gcc`, скриптов из `tests/src_c/...`;
   - любые интеграционные шаги, где важен **код возврата процесса**, а не текст AST.

В документе про тестовую систему это прямо разводится: текстовые ожидания для in-process стадий и **объектный** `exitCodeShouldBe` как инфраструктурный режим для внешнего процесса; затем к нему добавили реальный executor (`rawSystem` в `ManifestRunner_test`).

**Почему сейчас выглядит «пустым»**

В `test-manifest.json` стоит учебный пример с `whoami`: он только показывает, что ветка `Process` **работает**. Реальной пользы для репозитория мало — это **заготовка контракта**, а не тест компилятора.

**Итог:** `Process` — это **хук для интеграционных / CLI-тестов из одного манифеста** рядом с golden-тестами лексера/парсера. Если вы не планируете гонять внешние команды через этот JSON, кейс можно убрать или заменить на осмысленный (например, запуск вашего `Main` с фикстурой и проверкой exit code) — иначе он только шумит в отчёте.

## Что такое `Process` в манифесте

Один вызов `rawSystem`, проверка **только** exit code. Ни цепочки стадий компилятора в памяти, ни сравнения с эталонным выводом, ни гибкости «как pipeline» из коробки. **Гибче pipeline-тестов он не является** — наоборот, **проще и уже**.

Смысл одной команды в текущем виде — по сути **демонстрация поля в JSON** и точка расширения: «сюда можно будет повесить реальный CLI / внешний компилятор». Практической ценности как у полноценного pipeline у этого куска мало, пока не нарастите сценарий (скрипт, несколько шагов, захват вывода, эталоны).

## Сводка

| | Pipeline (`Pipeline_test`) | Манифест `Lexer`/`Parser` | Манифест `Process` |
|--|--|--|--|
| Где живёт логика | Haskell-спеки | JSON + общий раннер | JSON, одна внешняя команда |
| Что проверяется | Поведение функций по стадиям | Текст vs эталонный файл | Код выхода процесса |
| «Гибкость» | Полная (любой код в `it`) | Данные и режимы сравнения | Пока минимальная |

Итого: **от одной команды в чистом виде смысла мало** — согласен с вашей интуицией. Это **не аналог** вашего pipeline-теста и **не более гибкая** замена; это **другой слой** (внешний OS-процесс), который пока почти не использован. Имеет смысл либо наполнить его реальным сценарием (один скрипт = вся «последовательность»), либо расширять формат, либо убрать из манифеста, чтобы не вводил в заблуждение.

**Альтернатива по духу «гибкий pipeline»:** держать цепочку в `*.ps1` / `just` recipe и из теста только проверять артефакты и коды — или развивать `SystemPipeline_spec` и манифест отдельно под e2e, с явной моделью шагов, а не притворяться, что одна `rawSystem` уже pipeline.
