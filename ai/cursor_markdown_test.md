## `OK (golden, дампер не запускался)` — fixture-строки

**Golden** — эталонный файл рядом с `.c`:

- `test6.c` → `test6.ast` (или `.p`, `.l`)

В колонках «Ожидание» и «Выход» лежит содержимое этого golden-файла.

**Задумка генератора для fixture:**

1. Прогнать реальный lexer/parser (скрипт `DumpFixtureOutputs.exe`).
2. Сравнить результат с golden.
3. Если совпало — `OK (прогон DumpFixture)`.

**«Дампер не запускался»** значит: шаг 1 не дал данных — exe не собрался, упал, или JSON не сопоставился с путями. Тогда скрипт **не вычислял** выход, а **подставил golden в «Выход»** (out = exp). Совпадение формальное: файл сравнили сам с собой.

Итого: fixture **предназначен** для прогона, но в момент сборки таблицы прогона не было → честная пометка «golden, дампер не запускался». Это **не** провал `test6.c` в cabal test; в `cabal test test-parser` fixture может быть зелёным.

## `OK (из *_test.hs; прогон не выполнялся)` — unit-строки

**Источник** — не golden на диске, а **текст теста** в Haskell:

- `AST_test.hs`, `Lexer_test.hs`, `Parser_test.hs`, …

Генератор **переписал** в таблицу то, что в `shouldBe` / `Right (...)` в исходнике. Колонку «Выход» заполнил **копией** «Ожидания» — не вызывая `parseDeclFromTokens`, `lexerPure` и т.д.

**«Прогон не выполнялся»** = Python-скрипт **не запускал** компилятор на этой строке. Статус «всё совпало» — потому что выход **заранее** записан как ожидаемый, а не получен прогоном.


## 2. Web-отчёт уже содержит *все* тесты (не только провалы)

`test-web-report` (`WebReport_spec.hs` + `tasty-html`) после `just test-web-report` даёт, например:

> **All 78 tests passed**

В HTML — **дерево всех кейсов** с ✓, включая fixture, manifest, pending.

Ограничение не в «показываем только failed», а в **формате**:

| Есть в `test-report.html` | Нет в `test-report.html` |
|---------------------------|---------------------------|
| имя теста, PASS/FAIL/PENDING | Вход |
| при pending — текст TODO | Ожидание |
| при FAIL — обычно diff из hspec | Выход при PASS |

`hspec` + `tasty` **не сохраняют** при успехе пары «вход / ожидание / факт» — только факт «прошёл». Поэтому таблица с тремя колонками **не вырастет** из текущего HTML сама собой.

Нюанс UI: если есть **хотя бы один FAIL**, скрипт в HTML сворачивает зелёные группы (`rollup`) — прошедшие в DOM есть, но спрятаны. При полном зелёном прогоне всё развернуто.

## 4. Архитектура, которую я бы защищал (и где сомнение к «только web»)

**Центр — не HTML и не Python, а JSON после прогона.**

1. **Прогон** — тот же `test-web-report` (уже объединяет Lexer, Parser, AST, manifest, …).
2. **Запись фактов** — в момент проверки в Haskell, не постфактум:
   - обёртка вроде `assertGoldenRecord name input run expected` или
   - `tasty` ingredient, который на каждом leaf пишет запись в `IORef` / файл.
3. **Фикстуры** — как сейчас в тесте: прочитать `.c`, прогнать **тот же** пайплайн, что в `assertFixtureByPath` / `assertLexerManifestCase`, положить `show actual` в `actual`, golden в `expected`.
4. **Unit** — перед `shouldBe` явно сохранить вход и оба значения (или только `actual`, `expected` из выражения).

**Важно:** у вас **не один** пайплайн на все строки:

| Тест | Что вызывать |
|------|----------------|
| Lexer fixture | `lexerPure` на сыром `.c` |
| Parser fixture | `lexer` → `parseTokens` (без preprocess в коде fixture) |
| AST / preprocess | `preprocess` → `lexer` → … |
| `parseDeclFromTokens` | только токены, без файла |

Поэтому «вызвать функции» = **повторить ровно тот же код, что в конкретном `it`**, а не один универсальный дампер. Отдельный `DumpFixtureOutputs` легко разъехаться с тестами — ты это уже видел на «дампер не запускался».

## 5. Сомнение к выбору «только web-отчёт»

Расширять **только** `tasty-html` — тесно: кастомных колонок там нет.

Разумнее:

| Вариант | Плюс | Минус |
|---------|------|--------|
| **JSON + HTML + MD** | один прогон, широкая таблица, CI может жрать JSON | нужен маленький Haskell-слой записи |
| **Только MD из Python с вызовом GHC** | быстро набросать | второй пайплайн, drift с тестами |
| **Только парсинг лога** | без изменения тестов | хрупко, нет данных на PASS |

Твоя интуиция «или лог, или web» — на полпути. **Лучше третье:** structured export **из** web-прогона, а markdown — **вид** на JSON.

Манифест (`test-manifest.json`) уже задуман под это (`reportPath`) — логично расширить схему: не только пути к файлам, а опционально `matrixPath` или вложенные записи после run.

## Утверждаем (рабочая модель)

| Слой | Роль |
|------|------|
| **Haskell-тесты + обёртка** | единственный прогон, фиксация фактов в JSON |
| **tasty-html** | человекочитаемый отчёт: кто упал, pending, дерево |
| **Python по JSON** | широкая markdown-таблица, сводки, diff-статистика |

**Принцип:** JSON пишется **всегда** (PASS и FAIL). HTML — для навигации по прогону. Markdown — для обзора на широком мониторе.

**Ограничение, которое стоит заложить сразу:** обёртка должна вызывать **тот же код**, что и конкретный `it` (lexer fixture ≠ parser ≠ preprocess+lexer). Иначе JSON снова будет «правдой», но не той, что проверяет hspec.
